# 25 и 30. Flutter: описание решения и тест-кейсы

Мобильной разработкой я пока не занимался. Здесь описываю предложенное решение,
опираясь на документацию Flutter. Это разбор задания, а не отчёт о готовом мобильном приложении.
В репозитории нет Flutter-проекта и результатов его запуска на Android/iOS.

## 25. Экран списка и подробностей

### Разделение ответственности

**Repository** выполняет HTTP-запросы к `/api/tasks` и `/api/tasks/{id}`,
преобразует JSON в модель `Task` и превращает сетевые ошибки в понятные ошибки приложения.
Он принимает объект отмены запроса; например, `CancelToken` при использовании Dio.

**Controller / ViewModel** хранит состояние: задачи, текущий фильтр, загрузка,
ошибка, следующая страница. Он решает, когда загрузить или обновить данные.
Для небольшого экрана достаточно `ChangeNotifier` и `provider`; отдельная сложная
архитектура в этом задании не нужна. Состояние обновляется новым снимком,
UI получает уведомление и перестраивается.

**UI** отображает состояние и передаёт события контроллеру. В `build()` нет запросов
и правил обработки HTTP. Первая загрузка выполняется один раз при создании контроллера.
Не следует запускать её заново при каждом перестроении или повороте экрана.

Список — `ListView.builder`, ключ строки — `ValueKey(task.id)`.
Для загрузки — индикатор, для пустого списка — пояснение, для ошибки — кнопка повторения.
Обёртка `RefreshIndicator` вызывает `controller.refresh()` и ждёт завершения его `Future`.
Чтобы свайп работал и на пустом/коротком списке, нужен прокручиваемый контейнер
с `AlwaysScrollableScrollPhysics`.

Нажатие на строку открывает экран подробностей по ID через `Navigator.push`.
Сам экран подробностей получает актуальные данные через repository и показывает
собственные состояния загрузки и ошибки. На возврате список сохраняет фильтр и
позицию; если в подробностях изменили данные, обновляется соответствующая запись
или выполняется один контролируемый refresh.

### Отмена и жизненный цикл

У каждого запроса есть номер поколения и собственный объект отмены:

```text
load(filter):
    отменить предыдущий запрос
    generation += 1
    my_generation = generation
    отправить запрос с новым объектом отмены
    после ответа:
        если disposed, экран неактивен или my_generation != generation:
            не применять ответ
        иначе обновить состояние и уведомить UI
```

Отмена экономит ресурсы, а сравнение поколений защищает от ответа, который успел
прийти до отмены. То же правило относится к обработке ошибки и завершению загрузки.

При `dispose()` контроллер помечается уничтоженным, увеличивает поколение,
отменяет запросы и освобождает подписки. Он больше не вызывает `notifyListeners()`.
Если UI использует `BuildContext` после `await` для навигации или сообщения,
нужно сначала проверить `context.mounted`. Проверка `mounted` не заменяет отмену запроса.

Переход в подробности через `push` обычно **не уничтожает** список:
он остаётся под новым маршрутом. Поэтому одного `dispose()` недостаточно для отмены
при временном уходе. Я бы использовал `RouteAware`: `didPushNext` приостанавливает
экран и отменяет его запрос, `didPopNext` активирует экран и при необходимости
обновляет список один раз. Точно так же нужно определить политику при уходе
приложения в фон через наблюдение жизненного цикла.

Обычный rebuild или поворот не должен уничтожать состояние контроллера.
Его область жизни соответствует маршруту. При окончательном удалении маршрута
он освобождается; при открытии нового списка выполняется новая первая загрузка.

## 30. Мини тест-кейсы

Перед проверкой: тестовый API или fake repository с управляемыми ответами,
пустым результатом, задержкой и ошибкой. Ниже — конкретные сценарии для Flutter.

| ID | Шаги | Ожидаемый результат | Уровень |
|---|---|---|---|
| F01 — загрузка | Открыть экран; задержать первый ответ | Видна загрузка, приложение не зависает; после ответа индикатор исчезает | Widget + integration |
| F02 — список | Вернуть три задачи | Видны три строки с правильными названиями и статусами; нажатие открывает нужный ID | Widget + integration |
| F03 — пусто | Вернуть `items: []` | Пояснение об отсутствии задач; нет бесконечной загрузки; свайп обновления работает | Widget, ручная проверка жеста |
| F04 — ошибка | Вернуть 500 / отключить сеть | Понятное сообщение и «Повторить»; приложение не падает | Widget + integration |
| F05 — повтор | После F04 вернуть успех, нажать «Повторить» | Новый запрос, ошибка исчезает, появляется список; без дубликатов | Widget + integration |
| F06 — свайп | Загрузить список, изменить ответ API, потянуть вниз | Один refresh, старые данные допустимы во время обновления; новый список после успеха | Widget + ручная на устройстве |
| F07 — быстрый фильтр | Задержать A, выбрать B, вернуть B, затем A | Отображается B; ответ A игнорируется, включая его ошибку и завершение загрузки | Unit контроллера + widget |
| F08 — уход при загрузке | Открыть экран и выйти до ответа, затем завершить ответ | Запрос отменён; нет `setState after dispose` / уведомления уничтоженного контроллера | Unit + widget |
| F09 — поворот | Со списком и во время загрузки перейти portrait → landscape → portrait | Нет обрезанного текста/переполнения; состояние и фильтр сохраняются; лишних запросов нет | Widget с двумя размерами + ручная Android/iOS |
| F10 — подробности и назад | Открыть задачу, вернуться | Сохраняются список, фильтр и позиция прокрутки; максимум один refresh по принятой политике | Integration + ручная |
| F11 — возврат после удаления маршрута | Закрыть список окончательно и открыть снова | Создан новый контроллер; одна первая загрузка; старый ответ не попадает в новый экран | Widget + integration |
| F12 — ошибка следующей страницы | Получить первую страницу, следующую вернуть с ошибкой | Первые строки сохраняются, видна ошибка продолжения; повтор дописывает данные один раз | Unit + widget |

### Что автоматизировать

Unit: смену состояний контроллера, игнорирование старого ответа, отмену и отсутствие
уведомлений после уничтожения. Fake repository должен позволять завершать запросы
в произвольном порядке.

Widget: загрузку, пустое состояние, ошибку, список, кнопку повторения,
навигационное событие с правильным ID и layout при разных размерах.

Integration: взаимодействие с тестовым API, авторизацию, переход в подробности и назад,
обновление и отсутствие дублирующихся запросов. Тесты должны проверять результат,
а не точное число перестроений виджетов.

### Что проверить вручную

На Android/iOS: реальный свайп и системную кнопку «Назад», ориентацию и системные
настройки её блокировки, уход в фон, возврат, плохую сеть, читабельность длинных строк,
масштаб текста, TalkBack/VoiceOver и плавность прокрутки.
Смена размера окна в веб-тесте не доказывает корректность нативного жизненного цикла.

### Что выполнено в этом репозитории

Аналогичные состояния списка реализованы в веб-клиенте и проверяются Playwright.
Тест `test_ui_narrow_and_wide_layout` проверяет ширину 390 и 844 px, а не поворот
настоящего Flutter-приложения. Все F01–F12 выше — предложенный Flutter-тест-план.
