# 26–29. Проверки и конкретные сценарии

Unit и интеграционные тесты запускаются через `python -m pytest -q`.
Все проверки, включая Chromium: `python -m pytest --ui -q`.
Детальные команды установки — в README.

Unit проверяет отдельную функцию или модель. Интеграционный тест проходит через
FastAPI и реальную временную SQLite. UI-тест управляет настоящим Chromium и HTTP-сервером.
Сетевые перехваты в UI используются только для ошибки и контролируемого порядка ответов.

## 26. Регистрация

| Уровень | Конкретные случаи | Ожидаемый результат |
|---|---|---|
| Unit | Нет обязательного поля; некорректный email; `2020-02-30`; завтра как дата рождения; короткий пароль | Ошибка валидации нужного поля |
| Unit | ` ALICE@EXAMPLE.COM ` | Сохранение нормализованного `alice@example.com` |
| Unit | Лишнее `is_admin` в JSON | Поле запрещено, нельзя назначить себе права |
| Интеграция | Корректная регистрация | `201`, профиль; затем успешный вход; пароль/хеш отсутствуют в ответе |
| Интеграция | Повторная регистрация и email с другим регистром | `409 email_taken`, ошибка поля email, в БД один аккаунт |
| Интеграция | Отправить плохие значения напрямую, обходя UI | `422`; пароль не отражается в сообщениях |
| UI | Отправить пустую форму | Ошибки под полями, фокус у первого проблемного поля |
| UI | Email без `@`, будущая дата, короткий пароль | Понятные сообщения до отправки запроса |
| UI | Занятый email; затем исправить только адрес | Ошибка рядом с email, дата остаётся; после исправления аккаунт создаётся |

Уникальность email обеспечивается ограничением БД. Два клиента не должны создать
два аккаунта, даже если проверки формы прошли одновременно.
Пароль хешируется Argon2; UI не может определять, занят ли email, без ответа backend.

## 27. Скидка

Условие не задаёт сумму порога и процент, поэтому пример явно принимает
порог `10000.00` и скидку `10%`. «От порога» означает **включительно**, то есть `>=`.
Функция `apply_discount(amount, threshold, rate)` позволяет задать другую политику.

| Сумма | Почему проверяем | Итог |
|---|---|---|
| `0.00` | Минимальная сумма | `0.00` |
| `9999.99` | Минимальный денежный шаг ниже порога | `9999.99` |
| `10000.00` | Точно на границе | `9000.00` |
| `10000.01` | Минимальный шаг выше | `9000.01` |
| `10000.05` | Округление половины сотой | `9000.05` |
| `20000.00` | Обычная сумма выше порога | `18000.00` |
| `-0.01`, `NaN`, `Infinity`, `1.001` | Некорректные деньги | `ValueError` |

Проверяется также другой порог/процент и неверная конфигурация: отрицательный
порог, нечисловое значение, ставка меньше 0 или больше 1.

Подходят **параметризованные unit-тесты**, анализ граничных значений и классы
эквивалентности. Сеть и БД для этой функции не нужны.
Используется `Decimal`, округление `ROUND_HALF_UP` до двух знаков; значения создаются
из строк/целых, не из `float`. В БД деньги хранятся целыми сотыми единицами.
Политика округления выбрана для примера и должна согласовываться с требованиями продукта.

## 28. Создание заказа

Вход: `product_id`, `quantity`, активная сессия, `Idempotency-Key`.
Цена и итог берутся на сервере. Один заказ содержит один вид товара.

| Сценарий | Ожидаемый HTTP-результат | Что проверить в БД |
|---|---|---|
| Товар есть, остатка достаточно | `201`, ID заказа и итог | Одна запись заказа, остаток уменьшен ровно на quantity |
| Заказ на весь доступный остаток | `201` | Остаток стал нулём, а не отрицательным |
| Остатка недостаточно | `409 insufficient_stock` | Остаток и количество заказов не изменились |
| Товар не существует | `404 product_not_found` | Заказ не создан |
| Quantity 0 / отрицательное / не целое | `422` | Никакого списания |
| Нет токена | `401` | Никакого списания или заказа |
| Нет ключа идемпотентности | `422` | Никакой записи |
| Повтор после потери ответа с тем же телом и ключом | `200`, первоначальный ID | Один заказ и одно списание |
| Тот же ключ с другим quantity/product_id | `409 idempotency_conflict` | Первый заказ не изменён |
| Два разных клиента покупают последнюю единицу | Один `201`, другой `409` | Один заказ, остаток 0 |
| Два одновременных повтора с одинаковым ключом | `201` и `200`, одинаковый ID | Один заказ и одно списание |
| Ошибка записи заказа после уменьшения остатка | `500`, без деталей БД | Транзакция откатилась, остаток восстановлен |
| Прочитать чужой заказ | `404` | Не раскрывать содержимое |

**Что проверять интеграцией:** не только HTTP-код, но и состояние БД после запроса.
Обе операции выполняются в одной транзакции. `BEGIN IMMEDIATE` в SQLite
сериализует записи; условное уменьшение остатка делает проверку и списание атомарными.
Если запись заказа не прошла, закрытие соединения откатывает незавершённую транзакцию.

Тест rollback создаёт временный SQLite trigger, который отклоняет `INSERT orders`.
Он проверяет настоящий механизм отката, а не mock функции БД.
Конкурентные тесты отправляют два запроса через `asyncio.gather` к одному приложению
с отдельными соединениями и общей временной БД.

Ключ уникален в пределах пользователя; повтор сверяет товар и количество.
В учебном сервисе ключ хранится вместе с заказом без срока удаления.
При тайм-ауте клиент повторяет с тем же ключом, при новой покупке создаёт новый.
При `503 database_busy` также сохраняется исходный ключ.

## 29. Изменение общей авторизации

Сначала запустить **unit-тесты общей библиотеки**: разбор токена, срок действия,
отзыв, отсутствующие обязательные поля, неверная подпись/алгоритм, если это JWT.
В этом проекте токены opaque, поэтому проверки подписи JWT к нему не относятся.

Далее — **контрактные и интеграционные тесты**: оба клиента отправляют корректный
`Authorization: Bearer ...`; одинаково обрабатывают `200`, `401` и отказ доступа.
Изменение библиотеки не должно менять поля ответа, срок сессии или права пользователя
без намеренного изменения контракта.

Регрессионный список:

1. Регистрация и вход, правильный и неправильный пароль.
2. Валидная, отсутствующая, неправильная, истёкшая и отозванная сессия.
3. Вход → получение задач → выход → повтор со старым токеном получает `401`.
4. Смена аккаунта: данные первого пользователя не появляются у второго.
5. Пользователь не получает чужую задачу/заказ, даже меняя ID напрямую.
6. Неизвестный формат заголовка отклоняется, ошибки не раскрывают токен/пароль.
7. На обоих клиентах при истечении сессии предусмотрен повторный вход, без бесконечных запросов.
8. Если есть refresh — обновление, параллельные попытки refresh, logout и отзыв.
   Здесь refresh не реализован: пункт относится к плану для системы с такой функцией.
9. Web: кнопка входа/выхода, очищение локальных данных и прямой переход по защищённой ссылке.
10. Mobile: безопасное хранение токена, холодный запуск, уход в фон/возврат и навигация.

В `tests/test_api.py` общий HTTP-сценарий параметризован меткой `X-Client: web/mobile`.
Метка используется только как имя варианта теста и **не даёт никаких прав**.
Реальные проверки идут через один bearer-механизм. Это проверка серверного контракта;
она не заменяет прогон нативного приложения или тесты отдельной общей клиентской библиотеки.
Два настоящих приложения и изменение общей библиотеки в условии описаны как сценарий,
а не как существующий код, который был предоставлен для исправления.

Веб-проверки находятся в `tests/test_ui.py`. Мобильные проверки выше — предлагаемый
регрессионный план. Нет заявлений, что они были выполнены на устройстве.
